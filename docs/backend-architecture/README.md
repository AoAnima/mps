# Архитектура бэкенда PhytoLedger (Go)

Дизайн-документ бэкенда маркетплейса редких растений: HTTP/WS/SSE-шлюз, сборка данных по
декларативным маршрутам из БД, блочный серверный рендер, доставка обновлений блоков на клиент.

**Статус:** v1.1 после состязательного ревью. Все главы используют общий контракт;
нормативные правки ревью — [00-contracts.md](./00-contracts.md) §13, бэклог до старта — [07-roadmap.md](./07-roadmap.md) §8.

---

## TL;DR — 7 решений, которые определяют всё остальное

1. **Один конверт, три транспорта.** HTTP, WS и SSE принимают и отдают одни и те же типы
   `Message` / `ViewDoc` / `Event`. Новый транспорт не требует нового API.
2. **Маршрут — данные, но исполняет его Go, а не БД.** Манифест маршрута живёт в PostgreSQL
   (версии, права, шаги DAG, блоки), а собирает данные `composer` — типизированно, с тестами,
   трейсами и кэшем. БД остаётся хранилищем, а не оркестратором.
3. **Блок (фрагмент) — единица адресации, рендера, кэша и обновления.** У блока есть id
   (`product.price`), версия контракта, JSON Schema данных, ETag и статус (`ok/empty/degraded/error`).
4. **Рендер — интерфейс сразу, сервис — потом.** `Renderer` отделён портом, но на старте живёт
   в том же процессе: два сетевых хопа на запрос не окупаются.
5. **Деньги — только HTTP-команда с `Idempotency-Key` + транзакция PostgreSQL + outbox.**
   WebSocket — доставка событий, а не источник истины. Ставка по WS запрещена архитектурно.
6. **Права трёхуровнево:** policy (RBAC/ABAC) → row filter (RLS) → column projection (allowlist).
   Ошибка на любом уровне не должна превращаться в утечку через кэш.
7. **Клиент тонкий и тупой:** ~10 KB JS, морфинг блоков, никаких бизнес-вычислений на клиенте,
   полная работоспособность без JS.

## Соответствие исходной постановке

Пользовательская схема была такой: *(1)* HTTP/WS/SSE-сервер аутентифицирует по ключам и
структурирует запрос в «Сообщение»; *(2)* БД анализирует адрес и права, находит маршрут и собирает
данные в JSON с ключами-идентификаторами HTML-блоков; *(3)* сервер отдаёт данные в сервис рендера,
тот рендерит блоки или всю страницу, клиент патчит блоки.

| Уровень постановки | Куда переехал | Что изменилось |
|---|---|---|
| 1. Сервер запросов | `gateway` + `hub` | Добавлены: единый `Message`, ticket для стримов, идемпотентность, rate limit |
| 2. «БД собирает по маршруту» | `composer` + маршруты в БД | Маршрут остался данными в БД, но сборка вынесена в Go (ADR-001) |
| 3. Рендер и патч блоков | `renderer` + клиентский runtime | Добавлены: контракт блока, ETag, seq, degraded-режим, resume стрима |

Подробный разбор — [00-overview.md §5](./00-overview.md).
