# 07. План внедрения: от контракта до продакшена

Правила, по которым составлен план:

1. **Вертикальные срезы.** Каждый этап заканчивается сценарием, работающим end-to-end (браузер → БД → HTML),
   а не «слоем, готовым на 80%».
2. **Рисковое — раньше.** Деньги, ставки и порядок событий проверяются на этапе 2, а не «когда будет время».
3. **Контракт раньше кода.** `00-contracts.md` заморожен до первой строки бизнес-кода: иначе каждый
   сервис обрастёт своим диалектом `Message`.
4. **Каждый этап имеет критерий приёмки в цифрах** — иначе этап не закрывается.

---

## 1. Состав команды и допущения

| Роль | FTE | Зона |
|---|---|---|
| Backend Go | 2 | gateway, composer, renderer, workers |
| Backend Go (real-time) | 1 | hub, ставки, чат, события |
| Frontend (JS/шаблоны) | 1 | templ-фрагменты, клиентский runtime |
| SRE/DevOps | 0.5 | инфраструктура, CI/CD, наблюдаемость |
| QA | 0.5 | контрактные, нагрузочные, e2e |
| Продукт/дизайн | — | вне плана |

Оценки — в человеко-неделях (ч-н) для команды из 4 инженеров. Сроки указаны как ориентир, а не обязательство.

## 2. Этапы

### Этап 0. Фундамент и один сквозной маршрут (2 недели)

**Цель:** доказать, что каркас «gateway → composer → renderer» работает на одном реальном сценарии.

| Работа | Результат |
|---|---|
| Репозиторий, layout `cmd/app`, `cmd/worker`, `internal/*`, миграции goose, `sqlc`, CI (lint, test, vuln) | скелет собирается и деплоится в dev |
| Заморозка `00-contracts.md` + генерация Go-типов из JSON Schema фрагментов | `internal/message`, `internal/view` |
| gateway: request_id/trace, cookie-сессия, CSRF, нормализация, rate limit (Redis Lua), problem+json | аутентификация и лимиты готовы |
| Резолв маршрута: таблица `routes`+`route_versions`, снапшот в памяти, `retired/draft` | маршрут меняется без релиза |
| composer: `plan.Compile`, DAG, `sql`-шаги, `errgroup`+`semaphore`, дедлайн | один маршрут исполняется |
| renderer: templ, реестр фрагментов, `RenderPage`, layout со слотами | HTML отдаётся |
| Маршрут `feed.home`: лента + баннер + топ-аукционы (3 блока) | **сценарий: аноним открывает главную** |
| OTel-трейс на запрос, span на шаг, метрики §10 контракта, дашборд в Grafana | видно, где время |

**Критерий приёмки:** анонимный запрос главной: p95 < 400 мс при 100 RPS на dev-стенде, 0 ошибок
в 10-минутном прогоне, трейс показывает 3+ шага, маршрут меняется через БД без перезапуска.

**Риск этапа:** преждевременная оптимизация рендера. Не трогаем — сначала сквозной путь.

### Этап 1. Блочный рендер и клиентский runtime (2–3 недели)

**Цель:** страница обновляется частями, без перезагрузки и без SPA.

| Работа | Результат |
|---|---|
| `X-PL-Mode: fragment` + `Accept: application/vnd.pl.viewdoc+json`, `Vary`, ETag/304 | один URL — два представления |
| `renderer.RenderFragments` (по списку id), изоляция ошибок фрагмента | частичный ответ |
| Клиентский runtime: перехват ссылок, `applyEvent`, morph, focus/scroll, `data-pl-*` | навигация без перезагрузки |
| Формы: progressive enhancement, команда с `Idempotency-Key`, 409/422 по полям | работают без JS и с JS |
| Страницы: `product.page`, `shop.page`, `feed.home` (полный набор блоков) | **сценарий: карточка товара и переходы** |
| Кэш: HTTP-кэш анонимных страниц + кэш HTML фрагментов (Redis), теги | повторный запрос дешевле |
| Деградация: skeleton, `X-PL-Degraded`, статусы `empty/error` | страница не падает из-за блока |

**Критерий приёмки:** переход лента → товар → назад: ≤ 1 сетевой запрос на переход, обновляются
только изменившиеся блоки; карточка товара p95 < 350 мс при 300 RPS; доля degraded < 0.5%;
работает при выключенном JS (полная навигация).

### Этап 2. Реальное время, аукционы, деньги (3–4 недели)

**Цель:** комната аукциона с живыми ставками и чатом, деньги не теряются и не дублируются.

| Работа | Результат |
|---|---|
| hub: WS-`/ws/v1` с ticket, `sub/unsub/ack`, лимиты, backpressure, коды закрытия | соединения держатся |
| SSE-`/sse/v1`, `Last-Event-ID`, resume из ring buffer | догон без потерь |
| NATS JetStream: `ev.*`, fan-out, `seq` на топик | события доставляются |
| Горячее состояние аукциона: Redis Hash + Lua CAS, сверка с PG | чтение стакана < 5 мс |
| Ставки: `POST /v1/auctions/{id}/bids`, идемпотентность, резерв средств, транзакция + outbox | **сценарий: ставка → у всех зрителей** |
| Таймеры: worker, антиснайпинг (+60 с), закрытие лота, создание заказа | аукцион закрывается корректно |
| Чат: история (партиции), дедуп `client_msg_id`, rate limit, модерация, tombstone | **сценарий: чат аукциона** |
| Клиент: оптимистичная ставка + rollback, таймер с коррекцией дрейфа, переподписка | UI не врёт |

**Критерий приёмки:** 5 000 WS-соединений на инстанс, ставка p95 < 150 мс от нажатия до события у
всех зрителей (p95), 0 дублей ставок при 200 повторных запросах с одним `Idempotency-Key`,
0 расхождений Redis/PG после 10 000 ставок, лаг событий p95 < 300 мс.

**Риск этапа:** гонки «последняя ставка перед закрытием». Тест: 50 одновременных ставок в
последнюю секунду — ровно один победитель, остальные получают `conflict.bid_too_low`.

### Этап 3. Коммерция: корзина, кошелёк, escrow, заказы (3 недели)

| Работа | Результат |
|---|---|
| Корзина с группировкой по магазинам, расщепление платежа | мульти-корзина |
| Внутренний кошелёк: `WalletTx` append-only, двойная запись, аудит | баланс сходится всегда |
| Escrow: холд → подтверждение получения → разморозка → спор/возврат | **сценарий: покупка с холдом** |
| Заказы: статусная модель, трек-номера, уведомления | дашборд продавца |
| Мульти-магазины: `shops`, категории, темы через design tokens | витрина магазина |
| Дашборд «Я продаю / Я покупаю»: сводная аналитика, фильтр по магазинам | маршрут с агрегатами |

**Критерий приёмки:** property-тест «сумма всех `WalletTx` = баланс» на 10 000 случайных операций;
повторная команда с тем же ключом не двигает деньги; таймаут клиента не приводит к двойному списанию.

### Этап 4. Реестр селекции, AI, модерация, поиск (3 недели)

| Работа | Результат |
|---|---|
| Реестр сортов: заявка, генетическое трио, статусы, админ-очередь | **сценарий: регистрация сорта** |
| AI-описание: асинхронная задача, Vision-LLM, лимиты, стоимость, fallback | кнопка «Помощь ИИ» |
| Поиск и фильтры: OpenSearch, индексация через outbox, релевантность | лента/поиск |
| Модерация UGC: жалобы, wordlist, очереди, аудит | безопасность контента |
| Блокчейн-анкоринг: очередь, ретраи, статус «подтверждено», идемпотентность по хэшу | плашка «запись подтверждена» |
| Заказ физического куба: заказ, трекинг, NFC/QR-паспорт | расширение после MVP |

**Критерий приёмки:** заявка проходит путь «черновик → ИИ → модератор → утверждено» с полным
аудитом; повторный анкоринг не создаёт вторую запись; поиск p95 < 120 мс.

## 4. Что сознательно НЕ делаем в MVP (cut list)

| Откладываем | Почему | Когда вернёмся |
|---|---|---|
| Отдельный сервис рендера | 2 сетевых хопа без выгоды на старте | этап 5, при необходимости |
| Мультивалютность (крипто-цены) | RUB достаточно, `Hints.Currency` уже есть | после этапа 3 |
| Шардирование БД | до 100k DAU хватает реплик | по метрикам |
| Собственный видеосервис | WebRTC/HLS — вендор | никогда (не наша зона) |
| GraphQL / публичный API | внутренний контракт проще | при появлении партнёров |
| Персонализация ленты ML | сначала правила | после накопления данных |
| Оффлайн-режим клиента | веб-приложение | по запросу продукта |

## 5. Риски и триггеры

| Риск | Вероятность | Влияние | Триггер/признак | Ответ |
|---|---|---|---|---|
| Манифесты маршрутов становятся «программой на YAML» | высокая | среднее | > 8 шагов или ветвления в манифесте | лимит шагов, вынос в именованный rpc-шаг |
| Гонки ставок / двойные списания | средняя | критическое | расхождение Redis↔PG, жалобы | PG-транзакция единственный арбитр, property-тесты |
| WS-соединения съедают память | средняя | высокое | RSS инстанса растёт без трафика | лимит байт на соединение, коалесинг, 4008 |
| Кэш отдаёт чужие данные | низкая | критическое | тест «аноним не видит X» упал | `vary` по auth_level, no-store для персонализации |
| Рендер становится узким местом | средняя | среднее | p95 renderer > 150 мс | кэш HTML, профилирование шаблонов, выделение сервиса |
| Команда «дорисовывает» контракты по-своему | высокая | высокое | расхождение типов между сервисами | контракт заморожен, codegen, контрактные тесты в CI |
| Блокчейн-анкоринг блокирует заявки | низкая | среднее | очередь анкоринга растёт | асинхронность, статус «в очереди», деградация |

## 6. Definition of Done для любого этапа

1. Сквозной сценарий работает в staging на реальных данных (не моках) — и с JS, и без JS.
2. Контрактные тесты фрагментов против JSON Schema зелёные.
3. Трейс запроса показывает все шаги; метрики §10 контракта публикуются; дашборд обновлён.
4. Нагрузочный прогон этапа выполнен, цифры зафиксированы в README.
5. Runbook на новый тип отказа написан.
6. Нет `TODO` в путях денег, аутентификации и инвалидации кэша.

## 8. Бэклог по итогам ревью (закрыть до старта этапа 0)

Источник: [08-review.md](./08-review.md) §7. Пункты P0 блокируют этап 0 — без них команда начнёт
писать код под три разные схемы идемпотентности и два протокола ticket.

**P0 — блокируют этап 0**

1. `02 §2`: DDL + сид `query_registry` для шести запросов из `02 §8`; правило «новый запрос — PR с проекцией, `args_schema`, `checksum`».
2. Одна DDL `idempotency_keys` (02 §2), ссылки из 01 §6 и 06 §6.6; код `422 idempotency.key_reused` (контракт §13.4).
3. Один ticket-протокол (`POST /v1/realtime/ticket`, сабпротокол для WS), убрать Ed25519-ticket из 06 (контракт §13.3).
4. Рендер вызывает `gateway`, а не composer (контракт §13.2); согласовать схемы 01 §2 и 02 §8.
5. `503` для обязательного фрагмента до первого байта (контракт §13.8).
6. Trusted Types policy `pl` в клиентском морфе (контракт §13.11).
7. Admin-эндпоинт `?__explain`: версия маршрута, статус/латентность/кэш каждого шага, версии фрагментов, причина `degraded`. Без него эксплуатация ADR-001 нереальна.

**P1 — до публичного запуска торгов**

8. Модель холдов/escrow/`orders`/`WalletTx` (DDL + property-тест «сумма WalletTx = баланс»).
9. `outbox_lease(topic, owner, fencing_token, expires_at)` + `UPDATE … WHERE fencing_token = $1`.
10. Деньги в минорных единицах (`bigint`, копейки) во всех таблицах и на рендере — сейчас пять представлений.
11. RLS-политики для `auction_bids`, `chat_messages`, `orders`, `pii`; отдельный scope `pii.read`.
12. Загрузка медиа: presigned URL, лимиты типа/размера, EXIF-strip, антивирус, стоимость Vision-LLM.
13. Анти-бот на ставках: velocity, device-сигналы, shadow-limit.
14. `epoch` у `seq` + snapshot-протокол вместо догона при failover (контракт §13.1).
15. Синхронизировать профиль 10k vs 300k DAU в 06 §6.5/§6.9 и 07 §3 (в 00 §2 уже сделано).
16. Байтовый лимит очереди в `enqueue` (05 §5.11).

**P2 — после MVP**

17. Манифесты и запросы для `product.page`, `feed.home`, `shop.page` (детально описан только `auction.room`).
18. Социальный профиль (посты/лайки/альбомы): сущности, маршруты, модерация.
19. Мессенджер сделки: привязка к лоту, команда счёта.
20. Дашборд мульти-магазина: агрегатные запросы.
21. Реестр сортов + AI-очередь: таблицы задач, ретраи, стоимость.
22. Древо происхождения / блокчейн-паспорт: модель чтения и воркер.
